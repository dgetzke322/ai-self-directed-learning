- **How/Where:** Backend `SchedulerService` (in-process, no separate container); evaluates every `survey_config` against `next_fire_at`; creates `survey_instances` and `survey_tokens` rows

- **Data:** reads `responses`, no new columns
- **Why:** Prevents manager from reverse-engineering individual answers on 2-3 person teams

## 2. Assumptions Made NOT in the Product Description

### Entra ID Specifically
**Given:** "existing SSO system"  
**PRD chose:** OIDC auth-code flow against **Entra ID** specifically, using `openid-client` library

**Impact:** Reasonable for enterprise context (Improving's org uses Entra ID). Not guaranteed by description. If customer uses Okta/Auth0, requires adapter.

---

### In-Process Scheduler, No Redis/BullMQ
**Given:** "recurring pulse surveys with teams"  
**PRD chose:** Single in-process `SchedulerService` polling every 30 seconds; explicitly rejects Redis/BullMQ for V1

**Rationale stated:** "keep this a single-app-container deployment"

**Impact:** Removes operational complexity (no separate worker, no job queue infra). Bounds scalability (single instance only; multi-instance flagged as "revisit if scaling required").

---

### Single Docker Compose with Postgres Included
**Given:** "can be run locally, pre-compiled and easy to run with a single docker container"  
**PRD chose:** Multi-stage Dockerfile + `docker-compose.yml` adding Postgres 16 container with named volume

**Impact:** One-command local startup (`docker compose up`). No external DB required for development.

---

### Email as Primary, Slack as Webhook-Only
**Given:** "Engineers receive a notification (email or Slack)"  
**PRD chose:** Email is required channel (nodemailer to configured SMTP relay); Slack is optional, webhook-only (generic reminder, not per-user DMs)

**Rationale:** Webhook approach avoids Slack app OAuth complexity. Defers per-user DMs to Phase 2.

**Impact:** Clear delivery guarantee (email always works). Slack integrations limited in V1 scope.

---

### Minimum 4-Response Threshold for Anonymity
**Given:** "All responses are stored anonymously"  
**PRD added:** If response_count < 4, dashboard shows "Not enough responses to display results (minimum 4)"

**Rationale:** Prevents reverse-engineering on small teams (e.g., 3-person team: if avg=4.5, can infer individual's answer).

**Impact:** Not explicitly required but necessary for anonymity guarantee to hold in practice.

---

### Per-Team Timezone, Not Per-Member
**Given:** "weekly or bi-weekly schedule"  
**PRD chose:** `survey_configs.timezone` field; V1 assumes single timezone per team

**Impact:** Globally distributed teams would see survey send times in different local times. Scope boundary explicitly stated: "out of scope for V1."

---

### 50×15 Members Max Scale
**Given:** "solo developer to build, operate, and extend"  
**PRD chose:** "no degradation" benchmark assumes "50 teams × 15 members (750 members total) submitting concurrently"

**Impact:** Sets explicit boundary. Beyond 750 members requires multi-instance architecture (revisit only if scaling needed).

---

### 90-Day Retention for Archived Teams
**Given:** No data retention policy mentioned  
**PRD added:** "A manager can archive a team (soft delete via `teams.status`); archived team data purges after **90 days**, configurable via `RETENTION_DAYS` env var"

**Impact:** Introduces compliance posture (data not kept indefinitely). Value (90 days) is inference, not requirement.

---

### Removed Members Can Still Submit if Token Already Dispatched
**Given:** "Managers can configure… team membership"  
**PRD stated:** "if a member is removed after a survey has already dispatched, their outstanding token remains valid until it expires"

**Impact:** Documents out-of-scope edge case. Simplifies revocation logic; acceptable for V1.

## 3. Enterprise Context Missing (PM Would Always Add)

### 1. Audit Logging
**Gap:** No audit trail of manager actions (who created team, who changed survey config, when, what changed)

**Why enterprise needs this:** SOC 2 compliance, incident investigation, access control verification

**Implication:** Managers cannot answer "did someone change this config without my knowledge?" — forces trust assumption.

---

### 2. Backup/Restore Procedure
**Gap:** No documented backup strategy for Postgres volume; no restore procedure documented

**Why enterprise needs this:** Disaster recovery, data loss scenarios, regulatory retention proof

**Implication:** If Docker volume corrupts, data is unrecoverable. No documented RTO/RPO.

---

### 3. Database Migration/Upgrade Strategy
**Gap:** No documented procedure for deploying schema changes to production

**Why enterprise needs this:** Prisma migrations are mentioned (tool), but deployment ordering (create table → backfill → add constraint) not specified

**Implication:** Rolling back a bad migration, coordinating multi-instance deployments unclear.

---

### 4. RBAC Beyond Binary Manager/Engineer
**Gap:** Only two roles: manager (all access) and engineer (answer survey only)

**Why enterprise needs this:**
- Team lead: can view dashboard, cannot edit config
- Admin: can manage multiple teams across org
- Auditor: read-only view of all teams

**Implication:** All managers are super-users on their teams. No delegation or least-privilege roles.

---

### 5. Data Retention Policy for Responses (Not Indefinite)
**Gap:** "Survey responses are retained indefinitely by default" — no GDPR right-to-be-forgotten mechanism

**Why enterprise needs this:**
- GDPR: employees have right to deletion after employment ends
- CCPA: similar data minimization requirements
- Internal policy: "retain survey data for 2 years, then purge"

**Implication:** Compliance risk. No data deletion mechanism for individual responses.

---

### 6. Monitoring & Alerting
**Gap:** Only mentions `docker logs` for operations. No documented monitoring strategy

**Why enterprise needs this:**
- Alert if scheduler hasn't fired in 2 hours (stalled)
- Alert if survey response rate < 50% (low engagement)
- Alert if DB query latency spikes (degradation)
- Alert on TLS cert expiry

**Implication:** On-call team cannot proactively detect issues. Outages discovered by users.

---

### 7. Incident Response for Token Reuse
**Gap:** If someone tries to submit to `/api/survey/:token` twice, what happens? Can they see responses from other members?

**Why enterprise needs this:**
- Token leak scenario: what's the blast radius?
- Can a leaked token be exploited to gather intelligence?
- How do you revoke a single token retroactively?

**Implication:** Security posture unclear in adversarial scenarios.

---

### 8. Rate Limiting on Manager Endpoints
**Gap:** Only `/api/survey/:token` and OIDC callback are rate-limited. No rate limits on manager endpoints (`/api/teams/*`, `/api/trends`)

**Why enterprise needs this:** A malicious manager could DoS `/api/teams/:teamId/trends` with 1000 req/sec, or brute-force team IDs by guessing numbers

**Implication:** No protection against authenticated abuse.

---

### 9. Environment Variables Reference Guide
**Gap:** `MIN_RESPONSES_THRESHOLD`, `RETENTION_DAYS`, SMTP config, Slack webhook URL, Entra ID client secret all mentioned but scattered across sections

**Why enterprise needs this:** Operations team cannot deploy without centralized config reference (defaults, valid ranges, required vs optional)

**Implication:** Deployment documentation incomplete. Manual error-prone.

---

### 10. Load Testing / Performance Validation
**Gap:** "no degradation" at 50×15 concurrent, but no test results, methodology, or percentile breakdown documented

**Why enterprise needs this:** Who ran the test? On what hardware? What about p99 latency (vs p95)?

**Implication:** Performance claim is aspirational, not validated.

## 6. Raw Test Criteria for Exercise 5 Iterations

### Test Case 1: Audit Logging
**Input:** Add audit logging for manager actions (who, what, when)

**Expected Output Criteria:**
- Audit table schema (manager_id, action, timestamp, old_value, new_value)
- Endpoints that mutate state log to audit (team creation, config changes, member removals)
- Read audit via `GET /api/admin/audit-log` (manager-scoped)
- Retention: audit logs never auto-purge (indefinite)

**Failure Criteria (must NOT occur):**
- Audit log missing for team creation
- Audit log missing for survey config changes
- Timestamp is not precise (seconds only, not milliseconds)
- Audit visible to non-managers

---

### Test Case 2: Backup/Restore Procedure
**Input:** Document backup and restore strategy for Postgres data

**Expected Output Criteria:**
- Backup frequency (daily, weekly, on-demand)
- Backup method (pg_dump, WAL archiving, snapshots)
- Restore procedure (step-by-step)
- RTO/RPO targets (e.g., "RTO 4 hours, RPO 24 hours")
- Testing schedule (quarterly restore drills)

**Failure Criteria (must NOT occur):**
- No backup method specified
- Restore procedure missing or incomplete
- RTO/RPO not stated
- No test schedule

---

### Test Case 3: RBAC Beyond Manager/Engineer
**Input:** Add role-based access control for managers, team leads, admins

**Expected Output Criteria:**
- Four roles defined: super-admin, manager, team-lead, engineer
- Super-admin: manage multiple teams across org
- Manager: create teams, edit survey config, view dashboard
- Team-lead: view dashboard only (no edit)
- Engineer: answer survey only
- Each role maps to explicit API scopes (which endpoints are callable)

**Failure Criteria (must NOT occur):**
- Roles not defined
- No API endpoint scoping per role
- Manager can elevate other managers to super-admin without audit
- Team-lead can edit survey config

---

### Test Case 4: Data Retention Policy & GDPR Right-to-Deletion
**Input:** Add data retention policy and GDPR compliance for response deletion

**Expected Output Criteria:**
- Retention policy: responses retained for configurable duration (default 2 years)
- Deletion procedure: `DELETE /api/admin/responses/:employeeId` removes all responses for that employee
- Audit trail: deletion logged with timestamp and requesting admin
- Cascading deletes: when employee is deleted from team, their responses auto-delete after retention period
- Compliance: no raw response data persists after deletion (checked via `SELECT * FROM responses WHERE …`)

**Failure Criteria (must NOT occur):**
- Retention duration not configurable
- Deleted responses still queryable
- Deletion not logged
- Deletion does not cascade to related records

---

### Test Case 5: Monitoring & Alerting
**Input:** Add monitoring and alerting for operational health

**Expected Output Criteria:**
- Metrics exposed: scheduler tick frequency, survey dispatch lag, DB query latency p95, response rate per survey
- Alerts configured for: scheduler stalled (no fire in 2 hours), response rate < 50%, DB latency > 1 second, TLS cert expiring in 30 days
- Monitoring backend specified (Prometheus metrics endpoint, or Datadog agent, or equivalent)
- Alert routing: critical alerts page on-call (via Slack, PagerDuty, or equivalent)

**Failure Criteria (must NOT occur):**
- No metrics exposed
- No alerting rules defined
- Monitoring backend not specified
- Critical alerts not routed to on-call

---

### Test Case 6: Incident Response for Token Reuse
**Input:** Document security posture and incident response for leaked survey tokens

**Expected Output Criteria:**
- If token submitted twice: second request rejected with 410 Gone (resource already used)
- Token reuse cannot reveal other members' responses (schema isolation enforces this)
- Token revocation procedure: admin can revoke outstanding tokens via `POST /api/admin/revoke-token/:tokenId`
- Revocation audit: logged with reason and revoking admin
- Leaked token scenario: response limited (token can only submit once, expires after close_at, cannot enumerate member IDs)

**Failure Criteria (must NOT occur):**
- Double-submit accepted (idempotency without intent)
- Token reuse leaks other members' answers
- No token revocation procedure
- Revocation not logged

---

### Test Case 7: Environment Variables Reference Guide
**Input:** Add centralized environment variable configuration documentation

**Expected Output Criteria:**
- Table format: VAR_NAME | Type | Default | Valid Range | Required? | Purpose
- All env vars documented: MIN_RESPONSES_THRESHOLD, RETENTION_DAYS, SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASSWORD, SMTP_TLS, SLACK_WEBHOOK_URL, DB_CONNECTION_STRING, PORT, NODE_ENV, SESSION_SECRET, OIDC_CLIENT_ID, OIDC_CLIENT_SECRET, OIDC_ISSUER_URL, etc.
- Defaults specified for optional vars
- Validation rules (e.g., `MIN_RESPONSES_THRESHOLD` must be 1-50)

**Failure Criteria (must NOT occur):**
- Env vars documented in only 1 section (scattered across multiple places)
- No default values specified
- No validation rules
- Required vars not marked as such

---

### Test Case 8: Load Testing / Performance Validation
**Input:** Document performance testing methodology and results

**Expected Output Criteria:**
- Test scenario: 50 teams × 15 members, all submitting within 1-hour window
- Hardware: spec'd (EC2 instance type, or equivalent; DB instance size)
- Results: form load (p50, p95, p99), trends query (p50, p95, p99), error rate
- Concurrency model: ramping up over time vs. simultaneous burst
- Repeatability: test run 3 times; results consistent within 5%

**Failure Criteria (must NOT occur):**
- No test results provided
- Hardware not specified
- Only average latency reported (need percentiles)
- No error rate documented
